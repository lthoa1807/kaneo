# Kaneo Dashboard — Architecture (Phase 1)

> Phase: 1 – Architecture and Functional Specification
> Status: Implemented (Phase 3–5, `feature/ui-development`); awaiting final review.
> Inputs: `project-spec.md`, `technical-assessment.md` (§12.2, §12.3)
> Scope: v1 = Overview page + 11 widgets, backed by 2 new read endpoints.

## 1. Placement and routing

The Dashboard is a new page beside the existing Home page; Home is untouched.

| Item | Value |
| --- | --- |
| Route file | `apps/web/src/routes/_layout/_authenticated/dashboard/workspace/$workspaceId/overview.tsx` |
| URL | `/dashboard/workspace/$workspaceId/overview` |
| Sidebar label | "Overview" (`navigation:sidebar.overview`) |
| Parent layout | `dashboard/workspace/$workspaceId.tsx` (`<Layout>` + sidebar) |

Why a file route: the route tree is generated by `@tanstack/router-plugin`
(`routeTree.gen.ts`), so a new file needs no manual router registration. The
parent already enforces authentication and mounts the workspace shell; the
page only has to resolve `workspaceId` and render.

No route guard is added beyond what the parent provides. Data queries are
disabled for guests (section 7), and the API enforces permissions anyway.

## 2. Navigation

`apps/web/src/components/nav-main.tsx` builds `NavItem[]` for the staff nav.
Add one entry after Home:

```ts
{ title: t("navigation:sidebar.overview"), icon: LayoutDashboard,
  url: `${homeUrl}/overview` }
```

`isActive` already compares `pathname === item.url`, so `/overview` does not
light up Home. Guests (`staffNav === false`) never see the entry; their page
access is blocked by the same rule plus API authorization.

## 3. Component architecture

One component per file, pure helpers next to their use, tests beside them.

```
apps/web/src/components/dashboard/
  widget-card.tsx            card surface + heading shared by every widget
  widget-error.tsx           per-widget error + retry
  metric-tile.tsx            label + value + hint, one reusable tile
  deadline-risk.tsx          overdue-urgent + due-soon counts
  priority-donut.tsx         priority mix (inline SVG, legend carries values)
  due-load-chart.tsx         seven-day due buckets (CSS columns)
  project-load-chart.tsx     open tasks per project (progress bars)
  intake-queue.tsx           waiting + in-progress intake requests (three queries)
  task-drilldown.tsx         native <dialog> task list behind any count
  dashboard-skeleton.tsx     loading grid
  types.ts                   shared Drill / DrillFilters types
```

The unassigned count (widget 7) is a `MetricTile` in the top grid, not a
separate file. The page header is local markup in `overview.tsx`.

No new UI primitive is introduced. Widgets compose `card`, `skeleton`,
`button`, `empty` and native `<progress>`. Charts are one inline SVG donut and
two CSS layouts; there is no chart library and no shared chart abstraction
until a third chart needs one.

## 4. Data flow

```
route component
  ├─ useGetProjects({ workspaceId, enabled }, false)  → project count
  ├─ useGetActiveWorkspaceUsers(workspaceId)         → member count
  ├─ useGetAssignedTasks(workspaceId, true, enabled) → my open total
  ├─ useGetIntakeRequests({ status }) ×3             → waiting + in-progress queue
  └─ useGetDashboardSummary(workspaceId, enabled)    → counts, rows and chart buckets
```

The last two items are new. The new hooks and fetchers:

```
apps/web/src/fetchers/dashboard/get-dashboard-summary.ts
apps/web/src/fetchers/dashboard/get-dashboard-task-drilldown.ts
apps/web/src/hooks/queries/dashboard/use-get-dashboard-summary.ts
apps/web/src/hooks/queries/dashboard/use-get-dashboard-drilldown.ts
```

Query key: `["dashboard", workspaceId]`. No client-side aggregation: the
endpoint returns the bucket totals and rows, so the page never re-filters a
truncated task list to invent a number.

## 5. API surface

| Endpoint | Status | Use |
| --- | --- | --- |
| `GET /project?workspaceId` | exists | project count, per-project load |
| `GET /workspace/{id}/members` | exists | member count |
| `GET /task/assigned?workspaceId&countOnly` | exists | my open task count |
| `GET /workspace/{id}/intake-requests?status=…` | exists | intake queue (three statuses) |
| `GET /workspace/{id}/dashboard` | **new, read-only** | my overdue, overdue-urgent, due-soon, unassigned; priority, due-day and project charts |
| `GET /workspace/{id}/dashboard/tasks` | **new, read-only** | first 50 tasks behind one chart segment |

The new endpoints are the only API change. Their contract is in
`api-contract.md`; metric definitions are in `data-model.md`. They live in
`apps/api/src/workspace/` (routes in `index.ts`, schema in `schema.ts`,
controllers in `controllers/get-dashboard-summary.ts` and
`controllers/get-dashboard-task-drilldown.ts`) and share
`projectAccessCondition` through `controllers/dashboard-task-rows.ts`.

## 6. Caching and refresh

- Follow `useGetProjects(..., true)`: `refetchInterval: 30_000`,
  `refetchOnWindowFocus: "always"` while the page is visible.
- `staleTime` stays at the global default; the page is read-only.
- No WebSocket subscription in v1. The dashboard shows counts, and the 30 s
  poll is cheaper than wiring every task event into a second cache path.
- No server-side cache: one grouped SQL statement is cheaper than keeping
  aggregates fresh in Redis, and Redis must stay optional.

## 7. Authorization

- Queries use `enabled: ready && staffNav`, mirroring the Home page
  (`useIntakeSurfaces()` + `navForSurfaces`). Disable, do not merely hide.
- The new route uses
  `workspaceAccess.fromParam("workspaceId")` +
  `requireWorkspacePermission({ project: ["read"], task: ["read"] })`.
- The controller applies `projectAccessCondition(userId, taskTable.projectId)`,
  so a member limited to selected projects counts only those projects.
- Archived projects and `done`/`archived` tasks are excluded in SQL.
- A guest receives 403 from the endpoint; the UI never renders zeros as if
  they were data.

## 8. Loading, empty and error states

- First load: `dashboard-skeleton.tsx` with the same grid shape as the real
  page, so layout does not shift.
- Widget with a zero result: the tile renders `0` with its normal label. Only
  "no projects yet" gets an explicit empty message.
- Query error: `widget-error.tsx` replaces the affected widget (not the
  whole page) with a retry button; the other widgets keep their data.
- Partial data (one query failed) must not show a misleading total.

## 9. i18n, theme and accessibility

- All copy goes into `i18n/en-US.json` under a new `dashboard` namespace;
  translations for the other 20 locales come from `pnpm i18n:check:fix`.
- Colors come from existing tokens only: `--chart-1..5`, `--success`,
  `--warning`, `--destructive`. Light/dark and the `modern` palette work
  without per-component overrides.
- Numbers are real text, not canvas/SVG text. The donut is `aria-hidden` and
  its legend carries every value; bars are native `<progress>` with
  `aria-label`. Urgency is never signalled by color alone — the label says it.
- Keyboard: every drill trigger is a real button and the drilldown is a native
  `<dialog>` (browser focus trap and focus return). The page adds no manual
  focus management.

## 10. Testing strategy

| Layer | Test | Where |
| --- | --- | --- |
| Series helpers | five priority rows, seven UTC day rows, truncation flag | `apps/api/src/workspace/dashboard-series.test.ts` |
| Authorization and scope | guest 403, member limited to a project counts only that project, archived project and done task excluded | `tests/api-integration/dashboard-summary.test.ts` |
| Drilldown endpoint | priority/project/day filters, done task excluded, guest 403, invalid day 400 | `tests/api-integration/dashboard-drilldown.test.ts` |
| Query hook | key, enabled gating, disabled for guests | `apps/web/src/hooks/queries/dashboard/use-get-dashboard-summary.test.tsx` |
| Widgets | value formatting, zero state, share, error state, drilldown row/truncation, row and backdrop clicks | co-located `*.test.tsx` in `apps/web/src/components/dashboard/` (8 files, 19 tests) |
| Gates | `pnpm i18n:check`, `pnpm openapi:check` | CI |

Focused tests locally; heavy suites and `tsc` for `apps/web` go to CI (WSL
memory limit, see `technical-assessment.md` §7).

## 11. Boundaries

In scope: the page, its widgets, two new read endpoints, nav entry, i18n keys.

Out of scope: replacing Home, workspace-wide status/priority distribution,
member statistics, time tracking, chart libraries, Astryx or any
new dependency, schema changes, WebSocket dashboard updates, filters (the page
is already workspace-scoped).
